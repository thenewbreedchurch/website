## Known limitations / deferred scope

- **Paystack / live online payment is not built.** `give` page shows bank-transfer details only (matching the legacy site's actual functionality — Paystack was present in the old code but commented out and never finished). The data model supports adding it later without a migration.
- **No kids'/children's ministry section** on First Timers — confirmed with the church that no such program currently exists; nothing was invented.
- **Partitioning** on high-growth tables (`EventRegistration`, `ContactMessage`, `NewsletterSubscriber`) is designed for (createdAt-first composite indexes) but not physically implemented — premature at current traffic. Revisit if registration volume grows significantly.
- **CSRF tokens are intentionally not implemented.** Next.js Server Actions verify the `Origin` header against the deployment origin by default, which covers same-origin mutation safety. The public forms (newsletter, contact, event registration) are anonymous by design — there's no ambient session to hijack. `/admin` is protected by a `SameSite=Lax`, `httpOnly` custom session cookie (hand-rolled in `lib/session.ts`, not NextAuth — see the decision log) plus the same Origin check. If an admin mutation is ever implemented as a plain Route Handler instead of a Server Action, add an explicit Origin/Referer check for it (the two CSV-export routes and the registrations export already do their own session check via `getSessionFromCookie()`, which is a stricter bar than Origin-checking alone).
- **Admin panel's `/admin/announcements/[id]/registrations/export` and `/admin/subscribers/export`** cap CSV exports at 5,000 / 20,000 rows respectively (bounded Prisma `take`, not a true unbounded streaming export) — revisit if either table ever approaches that size.
- **Registration `capacity` is not hard-enforced server-side** — the announcement detail page hides the registration form once the count reaches capacity, but two simultaneous submissions right at the boundary could both succeed (no DB-level check/lock). Low real-world risk at this scale; worth a `WHERE count < capacity` guard in `registerForEventAction` if it ever matters.
- **The admin dashboard's pageview tracking (`PageView` model, added 2026-07-24) has no bot filtering.** Any client that executes JS and requests a public page counts as a view, including crawlers/scrapers that run JavaScript — the numbers on the dashboard are raw hits, not filtered "real visitor" traffic. Acceptable at this scale; revisit if the numbers ever need to be more rigorous (e.g. a user-agent denylist, or a real analytics service).

## Decision log

- **Next.js (full-stack) over a plain Vite SPA + separate Express backend.** The user's original ask was React+Vite specifically, but a client-only SPA needs a bolt-on prerenderer to be indexable by search engines, and a public church site's traffic depends heavily on search ("church near me," etc). Next.js gives SSR/ISR, same-origin Server Actions (replacing Express + CORS entirely), and one deployable app instead of two. Confirmed with the user before building.
- **Postgres via Prisma over keeping Firestore.** The legacy site had subscriber data split across a flat JSON file and Firestore for the same concept — a real, live inconsistency. Consolidating into one relational store with real foreign keys (registrations → announcements) fixes this at the root and removes the `firebase-admin`/`firebase`/`googleapis` dependency tree (and its exposed service-account key) from the stack entirely.
- **No CSRF tokens** — see "Known limitations" above for the full rationale.
- **Redis is used for both caching and rate limiting** (one connection, two purposes) rather than standing up separate mechanisms — right-sized for this traffic level.
- **Migrations run automatically**: via a Docker entrypoint (`scripts/entrypoint.sh`, runs `prisma migrate deploy` before the app starts) for both local Docker and the production container image, and via the Vercel build command for the Vercel deployment path (`prisma migrate deploy && next build` — migrating at build time rather than serverless cold-start avoids concurrent-instance migration races).
- **Full custom admin panel over a headless CMS.** Postgres+Prisma was already required for transactional data (registrations, subscribers, contact messages); extending the same schema to cover editorial content preserves referential integrity a headless CMS wouldn't give for free, and avoids syncing two systems.

### 2026-07-23 — Phase B2: admin authentication (hand-rolled session system, not NextAuth)

Built the full admin login/session/lockout/password-reset system against the existing `AdminUser`/`AdminSession`/`AdminVerificationToken`/`AdminPasswordResetToken` models. **Deliberately not NextAuth** — the schema's precise lockout/mustChangePassword/idle-timeout requirements don't map cleanly onto NextAuth's adapter conventions, so this is a small, carefully-reviewed custom session system instead. **Parameters chosen and why:**
- Session absolute TTL: **7 days** (hard ceiling regardless of activity) — matches the brief exactly.
- Idle timeout: **`ADMIN_SESSION_IDLE_MINUTES` (env, currently 15)** — sliding window, re-touched on every validated request, enforced server-side in `getSessionFromCookie()` and fail-closed (idle/expired sessions are deleted from the DB on the read that discovers them, not just ignored).
- Lockout: **5 failed attempts → 15 minute lock**, counter reset to 0 when the lock is set (matches the brief's explicit numbers). Implemented with Prisma's atomic `increment` to avoid a read-then-write race on the counter under concurrent attempts.
- IP-based login rate limit: **8 attempts / 5 minutes** per IP (separate from and in addition to the per-account lockout — covers the "many accounts, one attacker IP" shape the lockout alone doesn't). Forgot-password rate limit: **4 requests / 15 minutes** per IP (email-bombing mitigation).
- Password policy: **≥12 chars, ≥1 letter, ≥1 number**, checked via `isPasswordStrong` on both reset and change flows.
- Verification token TTL **24h**, password-reset token TTL **1h** — matches the brief exactly; both single-use (`usedAt`) and hashed at rest (SHA-256, not argon2 — correct choice for high-entropy random lookup values rather than user-chosen secrets).

### 2026-07-25 — Full security audit and remediation

The user asked for a full security scan of both the public site and admin panel. Three parallel research passes covered auth/session/authorization, input handling/injection/XSS, and configuration/headers/secrets/rate-limiting — every finding confirmed by reading the actual code (file:line), not inferred from naming or comments. Fixed the 8 concrete findings; a full list of what was checked and confirmed already-safe (session entropy, cookie flags, password hashing, CSRF posture, secrets hygiene, `next/image`'s SSRF protection, and more) is preserved in this session's plan file for future reference rather than repeated here.

**Admin login lockout enabled a cheap, repeatable denial-of-service (High):** `actions/admin-auth.ts` locks an account for 15 minutes after 5 failed attempts, but the per-IP rate limit on the login endpoint (8 requests/5min) didn't prevent reaching that 5-failure threshold within one window — and the admin login email doubles as the site's public contact address, so the target is trivially discoverable. An attacker could keep the real admin locked out indefinitely for the cost of ~5 requests every 15-20 minutes. Fixed by tightening the login endpoint's rate limit to 4 requests/5min (strictly below the lockout threshold, so IP throttling now actually gates the ability to trip lockout at all) and adding an email alert (new `emails/admin-account-locked.tsx`, `lib/admin-email.ts`'s `sendAccountLockedEmail`) fired the moment an account locks, giving the admin visibility and a direct link to the one recovery path that already worked regardless of lockout state — `resetPasswordAction` was already confirmed to clear `failedLoginAttempts`/`lockedUntil` on a successful reset.

**Stored XSS via JSON-LD `<script>` tag breakout (High):** `app/layout.tsx` (site-wide) and `app/(site)/announcements/[slug]/page.tsx` both rendered structured data via `dangerouslySetInnerHTML={{ __html: JSON.stringify(jsonLd) }}` — `JSON.stringify` doesn't escape `<`, so an admin-entered value (e.g. `ChurchSettings.orgName`) containing the literal substring `</script>` would close the tag early and let anything after it execute as real HTML/JS, for every visitor to every page. Fixed with a new `safeJsonLdString()` helper (`lib/metadata.ts`) that escapes `<` to `<` — valid inside a JSON string, semantically identical, but neutralizes the breakout. **Verified live**: saved `ChurchSettings.orgName` to `The New Breed Church</script><script>alert(1)</script>` through the real admin Settings form, confirmed via DOM inspection on the public homepage that exactly one JSON-LD script tag exists (not split into two), the payload renders as an inert `<`-escaped string, and no second `<script>` tag was ever injected — then reverted the test value through the same form.

**CSV formula injection in admin exports (Medium):** `lib/csv.ts`'s `escapeCsvCell()` only handled `"`, `,`, `\n` — never neutralized a leading `=`, `+`, `-`, or `@`, which Excel/Google Sheets treat as the start of a formula (CWE-1236). All four export routes (contact messages, new-convert inquiries, subscribers, event registrations) serialize fully anonymous public-form input verbatim, so a visitor could plant a formula payload that executes when staff open the exported file. Fixed by prefixing any cell starting with those characters with a leading `'`, the standard mitigation — one change in the shared helper covers all four routes.

**`script-src 'unsafe-inline'` unconditional in CSP, including production (Medium):** `middleware.ts` allowed inline scripts everywhere, which is what would have made the JSON-LD XSS finding actually exploitable (CSP is supposed to block exactly this class of injected script even if an escaping bug slips through). Replaced with Next.js's documented per-request nonce pattern: `middleware.ts` mints a fresh `crypto.randomUUID()`-based nonce in production only (dev keeps `'unsafe-inline'`, since local tooling needs it and a real visitor never loads a dev build), forwards it via an `x-nonce` request header, and both JSON-LD pages read it via `headers()` and apply it to their `<script nonce={nonce}>` tag. Next.js automatically applies the same nonce to its own internal inline scripts once it detects one in the CSP header — no extra wiring needed. **Verified live** against a real production build (`next build` + the standalone server): confirmed the `Content-Security-Policy` response header carries `'nonce-...'` instead of `'unsafe-inline'`, and the same nonce value appears on 40+ script tags in the rendered HTML including the JSON-LD one.

**Stale, unused third-party domains in CSP (Low, folded into the same middleware.ts pass):** Google Analytics/gtag, Mixlr, Cookiebot, and `consentmanager.net` were still allowlisted despite zero references anywhere in current source (`consentmanager.net` was explicitly already replaced by the site's own first-party consent banner). Removed all of the above; kept only `self` and the two YouTube domains that are actually embedded.

**Email-verification token consumed on GET / page render (Low-Medium):** `app/admin/(auth)/verify/[token]/page.tsx` ran `verifyEmailAction` as a side effect of the Server Component rendering, so any link-scanner, email security gateway, or browser prefetcher following the emailed link would burn the single-use token before the real admin clicked it. Rebuilt as a client component mirroring the reset-password page's already-correct pattern — the token is only consumed on an explicit "Verify my email" button click. **Verified live**: loading the page now shows the button and does nothing to the token until clicked.

**Missing rate limiting on `resetPasswordAction`/`verifyEmailAction` (Low):** every other public auth action already rate-limited; these two didn't. Added the same `checkRateLimit()` pattern used elsewhere in the file (10 requests/5min per IP) for defense-in-depth, even though both consume a 256-bit random token that's infeasible to brute-force regardless.

**Vestigial unused env vars (Informational):** `NEXTAUTH_URL`, `NEXTAUTH_SECRET`, `ADMIN_TOKEN_SECRET`, and `ALLOWED_ORIGINS` were declared in `.env.example`, `.env`, and `apps/web/.env.local` but never read by any code (confirmed via grep) — leftover from before the app settled on its hand-rolled session system. **Root cause found afterward, in a follow-up session, for what the "stale image" verification trouble above actually was:** the Visit Us hero image was swapped two more times based on further user feedback, and kept appearing stale through `/_next/image` even after a genuinely fresh `next dev` process restart (confirmed via `ps`/`lsof` — only one `next-server` PID, started after the file changed) while the raw, non-optimized `/images/...` static path always served the correct new bytes immediately. The actual cause: Next.js 16 + Turbopack's dev-mode image optimizer cache lives on disk at `apps/web/.next/dev/cache/images/` — a different, newer path than the classic `.next/cache/images/` this project's own earlier lessons (see the Round 4 entry above) had already learned to check, which is why it was missed for so long. Unlike an in-memory cache, deleting the process doesn't touch it — it survives every `next dev` restart until the directory itself is deleted (`rm -rf .next/dev/cache/images`) or `next build`/a fresh `.next` wipe runs. Any time a `public/` image is swapped and the live site keeps showing the old one through `next/image` specifically (not through a direct static-path fetch), delete that directory first before spending time on browser-cache or server-restart theories.
